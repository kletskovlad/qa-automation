## Лабораторна робота №5

**Тема:** Автоматизація тестування REST API. Supertest, JSON Schema, Postman і Newman.

**Індивідуальний варіант:** №5 — `PUT /orders/:id`: повна заміна позицій замовлення з перерахунком суми та перевіркою ідемпотентності трьох однакових запитів.

### Реалізовані функції

- `createApp()` — фабрика Express-застосунку з ізольованим сховищем даних.
- `POST /auth/login` — автентифікація користувача та видача токена доступу.
- `POST /orders` — створення замовлення з перевіркою вхідних даних.
- `GET /orders` — отримання списку замовлень поточного користувача.
- `GET /orders/:id` — отримання замовлення за ідентифікатором.
- `PUT /orders/:id` — повна заміна товарних позицій із перерахунком вартості.
- `DELETE /orders/:id` — видалення власного замовлення.
- Реалізовано розрахунок знижок залежно від рівня користувача та суми замовлення.
- Реалізовано обчислення вартості доставки.
- Додано перевірку Bearer-токена для захищених маршрутів.
- Використано зберігання замовлень і токенів у пам'яті.

### Проведене тестування

- Використано `Supertest` та `Vitest` для автоматизованого тестування REST API.
- Перевірено HTTP-статуси `200`, `201`, `204`, `400`, `401` і `404`.
- Реалізовано перевірки п'яти рівнів: статус, структура, значення, заголовки та побічні ефекти.
- Використано `Ajv` і `ajv-formats` для перевірки відповідей за JSON Schema.
- Додано `additionalProperties: false` для заборони зайвих полів.
- Перевірено авторизацію без токена, із підробленим токеном і доступ до чужих замовлень.
- Реалізовано параметризовані тести валідації вхідних даних.
- Перевірено збереження змін через повторні GET-запити.
- Забезпечено ізоляцію тестів за допомогою окремого виклику `createApp()`.
- Проведено експеримент із витоком внутрішнього поля `ownerId`.
- Створено колекцію Postman і запущено автоматизовані перевірки через Newman.
- Налаштовано експорт результатів Newman у формат JUnit XML.

### Індивідуальний варіант №5

- Реалізовано ендпоїнт `PUT /orders/:id`.
- Новий список товарів повністю замінює попередні позиції замовлення.
- Після оновлення повторно обчислюються `subtotal` і `total`.
- Зберігаються початкові ідентифікатор замовлення та дата створення.
- Перевірено правильність перерахунку знижок і доставки.
- Три однакові PUT-запити повертають однаковий стан ресурсу.
- Повторні PUT-запити не створюють додаткових замовлень.
- Некоректні дані повертають `400 Bad Request`.
- Запити без токена або з підробленим токеном повертають `401 Unauthorized`.
- Спроба змінити чуже або неіснуюче замовлення повертає `404 Not Found`.
- Перевірено відповідність відповіді JSON Schema та відсутність поля `ownerId`.
- Додано три послідовні PUT-запити до колекції Postman.

- Перевірено повну заміну позицій замовлення та ідемпотентність PUT.

### Запуск сервера

```bash
npm start
```

Сервер запускається за адресою `http://localhost:3000`.

### Запуск усіх тестів

```bash
npm test
```

### Тестування індивідуального варіанта №5

```bash
npx vitest run tests/orders-put.test.ts --reporter=verbose
```

### Перевірка JSON Schema

```bash
npx vitest run tests/orders-schema.test.ts
```

### Запуск Postman-колекції через Newman

```bash
npx newman run postman/orders.postman_collection.json --reporters cli,junit --reporter-junit-export results/newman.xml
```

### Перевірка TypeScript

```bash
npx tsc --noEmit
```

### Основні файли лабораторної

- `src/app.ts` — реалізація REST API.
- `src/server.ts` — запуск HTTP-сервера.
- `tests/helpers.ts` — допоміжні функції тестування.
- `tests/orders.test.ts` — тести базових операцій API.
- `tests/orders-put.test.ts` — тести індивідуального варіанта №5.
- `tests/orders-schema.test.ts` — перевірка відповідності JSON Schema.
- `tests/schemas/order.schema.ts` — схема замовлення.
- `tests/schema.ts` — функція валідації відповідей через Ajv.
- `postman/orders.postman_collection.json` — колекція Postman.

### Висновок

У ході лабораторної роботи досліджено автоматизоване тестування REST API із застосуванням Supertest, Vitest, JSON Schema, Postman і Newman. Реалізовано перевірки HTTP-статусів, структури й значень відповідей, заголовків, побічних ефектів, автентифікації та авторизації.

За індивідуальним варіантом №5 реалізовано ендпоїнт `PUT /orders/:id`, який повністю замінює товарні позиції замовлення та перераховує його вартість. Ідемпотентність підтверджено трьома послідовними однаковими PUT-запитами, після яких стан замовлення залишався незмінним.

Експеримент із витоком `ownerId` продемонстрував можливість виявлення небажаних полів за допомогою JSON Schema. Автоматизовані перевірки засвідчили коректність реалізації: усі 101 тест Vitest і 36 перевірок Newman успішно пройдено.
